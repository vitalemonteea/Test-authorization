# 项目文件地图

> 用途：回答三个问题——**这个文件是什么、现在还作不作数、我要找的东西在哪**。
> 盘点时间：2026-11-09。范围：仓库内 220 个文件（不含 `.git`、`node_modules`、`dist`/`vendor` 内部、`.claude/worktrees`、`.opencode` 内部）。
> 维护规则：新增、移动、废弃文件时同步更新本表；每次需求评审后检查第 5 节“权威链”。

---

## 0. 先看结论

1. **当前权威只有两处**：V2 平台看 `docs/01-需求/REQ-V2_测试设备授权平台/测试设备授权平台V2需求明细.md`（V2.6）；解决方案型看 `docs/01-需求/REQ-SOL_解决方案型授权/解决方案型测试授权需求方案.md`（V2.2）。
2. **原型只有一个源**：`测试设备授权平台V2.html` + 7 个共享 js/css。`dist/`、6 个 zip、`index.html` 软链都不是源。
3. **其余文档分四类**：专题草稿、调研证据、交付物、历史归档。本表用状态列区分。
4. **仍需关注的三件事**：6 个 zip 全部早于当前源码（部署前必须重新打包）、约 30 份文档未入 Git（其中 4 份为导航文档）、两套运营看板的数据与说明已分叉。

---

## 1. 全景：四层结构

```
证据层                  规则层                需求层                      原型 / 交付层
─────────────────      ──────────────        ─────────────────────      ─────────────────────────
调研 xlsx / eml    →   安全方案规则 xlsx  →   V2 需求概述 + 明细      →   测试设备授权平台V2.html
VOC、会议纪要          单品审批规则 xlsx      解决方案型需求方案           7 个共享 js/css
运营数据截图           字段清单 xlsx          运营看板需求文档             tests/（269 用例）
                                            各专题草稿                   dist/ + zip + 操作手册
```

找东西时先判断它在哪一层：**证据 → 规则 → 需求 → 原型/交付**。跨层引用断裂的地方，就是最容易找不到、最容易用错的地方。

## 8. 维护规则（先按现状执行，目录重构方案见《目录规范建议》）

1. **新增需求文档**：先写 md，放到 `docs/01-需求/` 并在本表登记；如需 docx，由脚本生成，放进同级 `导出/`。
2. **新增专题**：文件名格式 `主题_文档类型_状态.md`，例如 `授权变更延期_产品规格_草稿_v1.2.md`；避免“终稿/最终/final”。
3. **修改需求**：在原文件上改，并在文首“版本变更记录”加一行；不要新建“xxx-新”“xxx-v2”。
4. **新增截图/流程图**：源文件（html/md/mermaid）与导出物（png/svg）分开存放，导出物注明生成日期。
5. **临时分析**：放 `工作区/`（gitignore，可整目录删除），不要混进 `docs/`。
6. **每次评审后**：更新本表的状态列和权威链；检查 `handoff.md` 的引用是否仍然有效。
