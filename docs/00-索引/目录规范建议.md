# AI 辅助下的 PM 目录规范建议

> 结论先行：**目录不是给人看的分类柜，而是给 AI 的“取数路径”。**
> 好的结构只做三件事：让 AI 每次开工知道读哪三份、让同一事实只有一个源、让过期的东西默认不进入上下文。
> 本文先给通用模板，再给本项目的落地版和分阶段迁移路线。
>
> **执行状态（2026-11-09）**：Phase 0 ✅ 已完成；Phase 1 ✅ 已完成（未跟踪文档已按 3.3 归位，`outputs/` 已拆分）；Phase 2 ✅ 已完成（33 个 `docs/` 内已跟踪文件 + 7 个根目录文档已迁入目标目录，引用同步完成）。

## 1. AI 到底怎么“找文件”

AI 不记得你的目录结构。每次新会话，它都从入口文件重新建立上下文。它最怕三件事：

1. **不知道读哪份**——同一需求有 `需求描述.md`、`测试授权V2.md`、`需求方案.md`、`需求方案（终稿）.docx`，文件名都像真的。
2. **读到过期的那份**——`（终稿）.docx` 反而比不带“终稿”的旧 3 周。
3. **把派生物当源**——改 `dist/index.html`、改脑图 md、改 `测试授权运营看板.html`（构建产物），下一次生成就被覆盖。

所以目录设计的目标不是“整齐”，而是**让正确的那份文件，在正确的时间，被正确地读到**。由此有三条硬约束：

| 约束 | 具体做法 | 反例 |
| --- | --- | --- |
| 入口稳定 | 根 `README.md`（人）+ `AGENTS.md`（AI）+ `docs/README.md`（状态总表） | 让 AI 每次全仓库扫描 |
| 单一事实源 | 一个需求一个文件夹；md 是源，docx 是导出；xlsx 是数据源，脑图是视图 | md/docx 双源手改 |
| 状态显性 | 文档头写“现行/待评审/草稿/已归档”；归档只读且 AI 默认不读 | 文件名写“终稿/最终/最新” |

## 2. 通用模板：六区 + 两入口 + 一个可丢弃区

适用于大多数“一个人 + AI”的产品项目，不依赖 Notion、数据库或任何外部系统：

```
项目名/
├── README.md                    # ① 人的入口：我要做什么 → 去哪（30 秒）
├── AGENTS.md                    # ② AI 的入口：开工读什么、禁改什么（路由 + 红线）
├── CLAUDE.md                    # 工具适配层，指向 AGENTS.md，保持薄
│
├── 00-上下文/                    # AI 每次开工先读的三页
│   ├── CURRENT.md               # 当前主线、权威文件、最近变更
│   ├── INDEX.md                 # 文件/需求状态总表（唯一状态源）
│   ├── 术语与口径.md             # 跨需求共享的业务名词
│   └── 决策记录/                 # ADR-YYYYMMDD-主题.md：为什么这样定
│
├── 01-需求/                      # 要做什么
│   ├── REQ-001_需求名/           # 一个需求一个文件夹（见 2.1）
│   ├── REQ-002_需求名/
│   ├── _需求池/                  # 未评审的原始诉求，先收后判
│   └── _待评审/                  # 已立项但未进基线的专题
│
├── 02-证据/                      # 为什么做、按什么规则做
│   ├── 调研/                     # 问卷 → 结论 → 分发凭证 → VOC 速览
│   ├── 规则与字段/               # 审批规则母版、字段字典
│   ├── 运营与埋点/               # 运营方案、数据基线
│   └── 分析过程/                 # 一次性对比包、确认表
│
├── 03-原型/                      # 怎么做（可运行代码；若工具链限制可留在根）
│   └── app/
│
├── 04-交付/                      # 给人看、给客户/领导的东西
│   ├── 操作手册/
│   ├── 部署包/                   # 当前 + 上一版回滚，附发布记录
│   ├── 需求文档导出/             # docx/PDF，只读
│   └── 汇报/
│
├── 05-归档/                      # 只读冻结区：被替代/结项/一次性产物
│   └── YYYY-MM-事件/
│
└── 99-临时/                      # AI 工作区：gitignore，可整目录删除
    └── YYYYMMDD-任务/
```

### 2.1 一个需求文件夹的固定结构

```
REQ-001_解决方案型测试授权/
├── README.md            # 状态卡：owner / 版本 / 状态 / 权威文件 / 测试映射 / 替代关系
├── 需求.md              # 需求正文（五段式或团队约定格式）
├── 验收标准.md           # AT-* 验收 ID，与 tests 一一对应
├── 设计/                 # 流程图源（md/mermaid）、方案、决策记录
├── assets/               # 导出的 png/svg、截图（源与导出分开）
└── 导出/                 # docx/PDF，只读，由脚本生成
```

为什么这样分：AI 接到“改解决方案型需求”时，只需要打开一个文件夹，就能同时拿到**需求、验收、设计、导出**，不用在四个按类型分的目录里拼上下文。

### 2.2 命名规则（5 条）

1. **目录**：两位序号 + 中文主题，如 `01-需求/REQ-SOL_解决方案型授权/`。序号留间隔（10/20/30），方便插入。
2. **文件**：`主题_类型[_日期].md`，如 `授权变更延期_产品规格_20261105.md`。
3. **版本只写文档头**，不写文件名。禁止 `终稿 / 最终 / 最新 / 新版 / 副本 / copy / final`。
4. **派生物必须可识别**：放 `导出/`，或文件名带 `_导出`、`_派生`。
5. **日期用 `YYYYMMDD`**，排序友好；归档目录用 `YYYY-MM-事件`。

### 2.3 状态与权威

- 状态只用五个词：**草稿 / 评审中 / 现行 / 已替代 / 归档**。
- 同一主题同一时刻只能有一份“现行”。
- 每份文档头固定四行：

```markdown
> 文档版本：V1.3
> 更新时间：2026-10-20
> 状态：现行（权威）
> 适用范围：测试设备授权平台 V2
```

- `docs/README.md`（或 `00-上下文/INDEX.md`）是唯一状态总表：文件｜版本｜状态｜源/导出｜替代关系｜是否已实现。
- 被替代的文件先登记替代关系，再移入归档；归档只读，AI 默认不读。

### 2.4 md / docx / xlsx 的处理

| 类型 | 谁是源 | 谁是导出/视图 | 规则 |
| --- | --- | --- | --- |
| 需求文档 | md | docx | 只改 md，用脚本生成 docx；禁止在 Word 里改完不回填 |
| 规则/字段/调研数据 | xlsx | md 脑图、html 视图 | xlsx 是唯一真源；脑图只作阅读，缺字段时以 xlsx 为准 |
| 流程图 | md（Mermaid）或 html | png / svg | 改图先改源，再重新导出；导出物标日期 |
| 手册 | docx 或生成脚本 | docx | 有脚本时脚本是源；无脚本时 docx 是源，标注“docx 为源，待转 md” |

### 2.5 AI 临时区

- AI 产生的文本抽取、ndjson、预览截图、一次性对比表，全部进 `99-临时/YYYYMMDD-任务/`。
- 该目录 gitignore，可随时整目录删除，不参与构建，不被需求文档引用。
- 内容如果要“转正”，按编号移入 01–04 并在索引登记；否则定期清空。
- **本项目 `outputs/` 失控的根因，就是没有这个区**：一次性分析、导出表、ndjson、预览图全堆在一个长期目录里。

## 3. 落到本项目：推荐结构

### 3.1 一个关键约束：运行区不能随便搬

这个仓库不是纯文档库，根目录同时是**可运行原型的运行根**：

- `scripts/build-static.cjs` 硬编码了 21 个根目录文件名；
- 25 个测试中的 12 个用相对路径读根目录原型/共享 js；
- `测试设备授权平台V2.html` 用相对路径加载 `info-collection-*.js`、iframe 加载 `operations-dashboard.html`；
- 根 `index.html` 是指向 V2 的符号链接，`npm run build` 依赖它作为入口别名。

所以我的建议是：**运行区冻结在原位，文档区彻底重构**。这牺牲一点“根目录视觉整洁”，换来 `npm test` / `npm run build` / 本地预览永远可用。等团队变大、需要多人协作时，再考虑把运行区整体搬到 `02-原型/app/`（见 4.4）。

## 4. 不推荐的做法

1. **按文件类型分目录**（`所有docx/`、`所有xlsx/`、`所有流程图/`）——AI 找一份需求要跨 4 个目录，人也一样。
2. **把所有东西塞进 `docs/` 一层**——就是现在的状态：主线、草稿、导出、历史混在一起。
3. **用“终稿/最终/最新/新版”命名**——本项目已经出现“（终稿）反而更旧”的真实事故。
4. **md 和 docx 双源手改**——改完 Word 不回填 md，下一次脚本生成就覆盖。
5. **把 zip、dist、截图提交进 Git**——仓库会迅速膨胀；用 `.gitignore` + 发布记录表。
6. **一次性大搬家再补引用**——先小步移动未跟踪文件，再动已跟踪文件，每步跑测试。
7. **建一堆空目录占位**——空目录不进 Git，只会制造“看起来有结构”的假象。
