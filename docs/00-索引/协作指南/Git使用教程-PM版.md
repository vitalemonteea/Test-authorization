# AI 协作版 Git 使用教程（PM 版）

这份文档给 PM、需求同学、项目协作同事使用。

现在我们的实际工作方式不是让每个人都背 Git 命令，而是：

> 你告诉 AI 你要做什么，AI 帮你检查、提交、建分支、合并；你负责确认改动内容和提交目的是否正确。

所以这份教程重点不是“学会所有 Git 命令”，而是教你：

- 第一次怎么准备 Git 环境
- 日常怎么让 AI 帮你操作 Git
- 你应该怎么描述需求
- AI 操作完后你要确认什么
- 哪些 Git 操作需要特别小心

---

## 1. 先理解我们的协作模式

传统 Git 教程会教很多命令，例如 `git add`、`git commit`、`git merge`。

但在我们现在的工作流里，PM 通常不需要自己手动敲这些命令。你更常做的是对 AI 说：

```text
帮我看一下当前 Git 状态。
```

```text
这版需求我确认了，帮我提交一下。
```

```text
帮我新建一个分支，准备做二阶段需求。
```

```text
帮我把这个分支合并到 master。
```

AI 会帮你执行 Git 操作，并告诉你：

- 当前在哪个分支
- 哪些文件被修改了
- 准备提交哪些内容
- 提交信息是什么
- 是否合并成功
- 有没有冲突或风险

你需要做的是确认这些信息是否符合你的真实意图。

---

## 2. 第一次使用前：让 Codex 检查并安装 Git

虽然日常操作由 AI 代劳，但电脑上仍然需要安装 Git。

你不需要自己先去找下载地址，可以直接对 Codex 说：

```text
帮我检查这台电脑有没有安装 Git。如果没有，请优先用 winget 安装 Git for Windows；如果需要我确认权限或弹窗，请先停下来告诉我。
```

Codex 通常会先检查：

```bash
git --version
```

如果没有安装，Codex 可能会使用 Windows 的 `winget` 安装：

```bash
winget install --id Git.Git -e --source winget
```

安装后，Codex 会再次检查：

```text
git version 2.xx.x
```

看到版本号，就说明 Git 已经可以使用。

如果电脑不能使用 `winget`，可以让 Codex 改用人工下载方式：

```text
这台电脑不能用 winget，帮我给出 Git 官网下载地址和安装选项，我按你的说明安装。
```

Git 官网地址：

```text
https://git-scm.com/download/win
```

安装完成后，再让 Codex 检查：

```text
帮我确认 Git 是否安装成功。
```

---

## 3. 第一次使用前：让 Codex 配置 Git 身份

Git 需要知道每次提交是谁做的。

你可以直接对 Codex 说：

```text
帮我配置 Git 用户名和邮箱，用户名是 xxx，邮箱是 xxx@xxx.com。
```

例如：

```text
帮我配置 Git 用户名和邮箱，用户名是 chris，邮箱是 2192189495@qq.com。
```

AI 会帮你设置，并检查是否配置成功。

背后通常会执行类似命令：

```bash
git config --global user.name "chris"
git config --global user.email "2192189495@qq.com"
```

Windows 环境建议顺手让 Codex 一起配置换行和拉取策略：

```text
帮我把 Git 的 Windows 换行和 pull 策略也配置成适合 PM 使用的默认值。
```

Codex 可能会执行：

```bash
git config --global core.autocrlf true
git config --global pull.rebase false
```

如果你不确定当前配置是什么，可以说：

```text
帮我看一下当前 Git 的用户名和邮箱配置。
```

---

## 4. 项目来自远端：让 Codex 帮你下载项目

如果你还没有项目文件，可以把项目地址发给 AI，然后说：

```text
帮我把这个 Git 项目下载到本地。
项目地址是：xxx
```

Codex 会帮你执行下载，并告诉你项目放在哪个目录。

背后通常会执行：

```bash
git clone 项目地址
```

如果项目需要登录，系统可能会弹出登录窗口或要求你输入账号。按公司的账号权限登录即可。

---

## 5. 项目来自本地文件夹：让 Codex 创建 Git 仓库

有些项目不是从远端下载的，而是本来就在本地，比如：

- 本地有一份原型文件夹
- 本地有一堆需求文档
- 本地有一个临时项目目录
- 之前没有 Git，现在想开始做版本管理

这种情况可以让 Codex 在本地文件夹里创建 Git 仓库。

推荐说法：

```text
这个项目目前只是本地文件夹，还没有 Git。请帮我检查当前目录是否已经是 Git 仓库；如果不是，就初始化 Git，并提交一版初始版本。
```

如果你知道目录路径，可以说得更明确：

```text
请把 D:\项目\测试授权 这个本地文件夹初始化成 Git 仓库，先检查里面有没有不该提交的临时文件，再创建第一版提交。
```

Codex 通常会做这些事：

1. 检查当前目录是不是 Git 仓库
2. 检查有哪些文件
3. 判断是否需要 `.gitignore`
4. 初始化 Git 仓库
5. 提交第一版

背后可能会执行：

```bash
git init
git status
git add .
git commit -m "chore: 初始化项目版本管理"
```

如果这个本地项目暂时只在自己电脑上使用，不需要远端地址，也可以先不配置远端。

如果后面要同步到公司 Git 平台，可以再对 Codex 说：

```text
这个本地仓库现在要关联远端地址，地址是 xxx。请帮我添加远端并推送 master。
```

背后通常会执行：

```bash
git remote add origin 远端地址
git push -u origin master
```

注意：本地文件夹初始化前，最好让 Codex 先检查是否有临时文件、导出文件、缓存文件，避免把无关内容提交进去。

## 6. 每天开始工作时，让 Codex 先检查状态

每天开始修改需求、原型、文档前，推荐先对 Codex 说：

```text
帮我看一下当前 Git 状态，确认我现在在哪个分支，有没有未提交内容。
```

AI 应该告诉你：

- 当前分支是什么
- 有没有未提交文件
- 哪些文件被修改了
- 是否适合继续工作

如果你准备开始一个新需求，可以说：

```text
我要开始做 XX 需求，帮我从 master 拉最新代码，并新建一个合适的分支。
```

AI 通常会帮你：

1. 切到 `master`
2. 拉取最新内容
3. 新建 `feature/xxx` 分支
4. 告诉你当前已经在新分支上

---

## 7. 我们的分支习惯

你不需要背太多分支规则，只要记住这几个名字。

| 分支类型 | 用途 | 例子 |
| --- | --- | --- |
| `master` | 主线，放已经确认过的内容 | `master` |
| `feature/...` | 正常需求或功能修改 | `feature/phase2-requirements` |
| `codex/...` | AI/Codex 辅助修改 | `codex/v1-prototype-updates` |

日常表达可以很简单：

```text
帮我基于 master 新建一个分支，用来做二阶段需求。
```

或者：

```text
这个改动是 AI 帮我做的，你帮我放到 codex 分支里。
```

---

## 8. 修改完成后：让 Codex 先总结改动

不要一改完就直接说“提交”。

推荐先说：

```text
帮我总结一下这次改了哪些文件、每个文件主要改了什么。
```

AI 会检查改动，并给你类似这样的总结：

```text
本次改动：
- 需求描述.md：补充二阶段授权规则
- 测试授权V2.md：调整多设备授权说明
```

你确认没有问题后，再说：

```text
确认，帮我提交。
```

这样可以避免把无关文件、临时文件、误改内容一起提交。

---

## 9. 让 Codex 帮你提交

最常见说法：

```text
这版我确认了，帮我提交一下。
```

更推荐说得具体一点：

```text
这版二阶段需求我确认了，帮我提交，提交信息写“feat: 补充二阶段授权需求说明”。
```

如果你不知道提交信息怎么写，可以说：

```text
帮我根据这次改动生成一个合适的提交信息，然后提交。
```

Codex 会根据改动内容选择类似下面的提交信息：

```text
feat: 补充多设备授权需求
fix: 修正客户搜索说明
style: 优化基本信息表单布局
chore: 保存合并前的本地修改
```

---

## 10. 我们常用的提交信息类型

PM 不需要记很多，只要知道大概含义。

| 前缀 | 什么时候用 | 例子 |
| --- | --- | --- |
| `feat:` | 新增需求、功能、说明 | `feat: 补充多设备授权需求` |
| `fix:` | 修正错误、补充遗漏、修复问题 | `fix: 修正设备ID字段说明` |
| `style:` | 样式、格式、布局调整 | `style: 优化基本信息表单布局` |
| `chore:` | 保存状态、整理文件、非业务修改 | `chore: 保存合并前的本地修改` |
| `merge:` | 合并分支 | `merge: xaas v1 prototype updates` |

你可以直接让 Codex 判断：

```text
帮我判断这次提交应该用 feat、fix、style 还是 chore。
```

---

## 11. 让 Codex 帮你合并分支

当一个需求分支已经确认完成，可以让 AI 合并到主线。

推荐说法：

```text
这个分支确认完成了，帮我合并到 master。
```

更稳妥的说法：

```text
这个分支确认完成了。请先检查当前状态，再切到 master 拉最新代码，然后把当前分支合并到 master。合并前如果有未提交内容先提醒我。
```

Codex 会帮你做这些事：

1. 检查当前有没有未提交内容
2. 确认当前分支
3. 切到 `master`
4. 拉取最新内容
5. 合并目标分支
6. 告诉你是否成功

如果合并成功，你可以继续说：

```text
确认没问题，帮我推送。
```

---

## 12. 合并前保存当前状态

有时候 Codex 会建议：

```text
chore: 保存合并前的本地修改
```

这是什么意思？

简单理解就是：在进行合并、切分支、复杂修改前，先把当前成果保存一份。

这是一种比较安全的习惯。比如你可以说：

```text
我后面要做合并了，先帮我保存一下当前状态。
```

Codex 会检查改动并提交一版，提交信息通常可以写：

```text
chore: 保存合并前的本地修改
```

---

## 13. 遇到冲突时怎么办

冲突就是：两边都改了同一个地方，Git 不知道该保留哪一版。

PM 不需要自己硬处理冲突。

如果 Codex 告诉你有冲突，你可以这样说：

```text
帮我说明一下冲突发生在哪些文件、冲突内容大概是什么，不要直接覆盖，先让我确认。
```

Codex 应该告诉你：

- 哪些文件冲突
- 冲突位置大概是什么
- 当前分支内容是什么
- 要合并进来的内容是什么
- 建议怎么保留

你确认后再说：

```text
保留你建议的版本，帮我解决冲突并提交。
```

或者：

```text
这里以 master 为准，帮我解决冲突。
```

如果冲突涉及重要需求逻辑，不要急着处理，先找相关负责人确认。

## 14. 常见你可以直接对 Codex 说的话

### 查看当前状态

```text
帮我看一下当前 Git 状态。
```

### 查看我改了什么

```text
帮我总结一下我这次改了哪些内容。
```

### 开始新需求

```text
我要开始做 XX 需求，帮我从 master 拉最新代码并新建一个分支。
```

### 提交当前修改

```text
这版我确认了，帮我提交一下。
```

### 指定提交信息

```text
帮我提交，提交信息是“feat: 补充XX需求说明”。
```

### 保存当前状态

```text
先帮我保存当前状态，避免后面合并丢东西。
```

### 合并到 master

```text
这个分支确认完成了，帮我合并到 master。
```

### 推送到远端

```text
确认没问题，帮我推送到远端。
```

### 查看最近提交

```text
帮我看一下最近 10 条提交记录。
```

### 出问题时

```text
先不要改，帮我解释一下现在 Git 卡在哪里。
```

## 15. Codex 操作 Git 时，你要重点确认什么

AI 执行提交或合并前，你最好看这几件事。

### 14.1 当前分支对不对

如果你要做新需求，通常不应该直接在 `master` 上改。

你可以问：

```text
我现在是不是在正确的分支上？
```

### 14.2 提交文件对不对

提交前确认有没有混入无关文件。

你可以问：

```text
这次准备提交哪些文件？有没有无关文件？
```

### 14.3 提交信息对不对

提交信息最好能看懂。

例如：

```text
feat: 补充二阶段授权需求说明
```

就比下面这种好：

```text
update
```

### 14.4 有没有高风险操作

如果 Codex 提到这些词，要停下来确认：

- `reset --hard`
- `clean`
- `force push`
- 强制覆盖
- 删除未提交修改

你可以直接说：

```text
不要执行高风险命令，先解释风险和替代方案。
```

---

## 16. 不建议 PM 直接让 Codex 做的事

下面这些话风险较高，不建议直接说。

### 不建议

```text
帮我强制覆盖远端。
```

```text
把本地改动都删了。
```

```text
直接 reset 掉。
```

```text
不管冲突，全部用我的版本。
```

### 推荐替代说法

```text
先帮我看看本地和远端差异，再告诉我有哪些处理方案。
```

```text
我想放弃某些改动，先列出来让我确认，不要直接删除。
```

```text
冲突先不要自动处理，帮我解释差异后再决定。
```

## 17. 一个完整的 Codex 协作示例

### 场景：我要补充一个新需求并提交

你可以这样和 Codex 对话：

```text
我要开始补充二阶段授权需求，帮我从 master 拉最新代码并新建分支。
```

Codex 处理完成后，你修改文档或让 Codex 修改文档。

改完后说：

```text
帮我总结一下这次改了哪些文件。
```

Codex 总结后，你确认没问题：

```text
确认，帮我提交，提交信息写“feat: 补充二阶段授权需求说明”。
```

如果需要合并：

```text
这个分支确认完成了，帮我合并到 master。合并前先检查是否有未提交内容。
```

合并成功后：

```text
确认没问题，帮我推送。
```

## 18. PM 最小 Git 知识

你只需要记住这几个概念。

| 名词 | 简单理解 |
| --- | --- |
| 仓库 | 这个项目的 Git 文件夹 |
| 分支 | 一条独立工作线 |
| `master` | 主线，放确认过的内容 |
| 提交 | 保存一次修改记录 |
| 合并 | 把一个分支的内容并回主线 |
| 冲突 | 两边改了同一处，需要人工确认 |
| 推送 | 把本地提交同步到远端 |
| 拉取 | 把远端最新内容同步到本地 |

---

## 19. 最后记住三句话

1. 不需要背 Git 命令，先学会把你的意图跟 AI 说清楚。
2. AI 提交前，一定确认分支、文件、提交信息。
3. 遇到冲突、覆盖、删除、强推这类操作，先让 AI 解释风险，不要直接执行。
