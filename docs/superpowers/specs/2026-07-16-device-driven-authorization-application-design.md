# 测试设备授权平台 V2：设备识别驱动的授权申请设计

> 日期：2026-07-16  
> 状态：已确认  
> 范围：产品授权申请页的产品线选择、设备识别、申请事项、多设备校验和审批决策  
> 规则来源：`测试授权申请审批规则与审批流.xlsx`

---

## 一、背景与目标

V1 的测试授权页面主要承接常规测试授权。V2 需要统一承接首次开通、授权延长、增开模块、扩大规格，以及销售设备相关的超规申请。

当前 V2 使用 `authScene`（授权场景）让用户在填写设备前选择业务场景。该字段同时混合了三类信息：

1. 设备事实：销售设备、借测设备、当前授权是否有效。
2. 用户意图：开通、延长、增开模块、扩大规格。
3. 流程结果：默认放通、人工审批、特殊流程。

设备事实可以通过设备 ID、借测系统及其他业务平台查询，流程结果应由审批规则计算，二者都不应由用户凭经验选择。用户只需要表达系统无法推断的本次申请意图。

本方案目标：

1. 降低授权场景误选风险。
2. 利用设备查询结果减少用户判断和重复填写。
3. 保留同一业务上下文下的多设备批量申请能力。
4. 阻止审批规则或处理流程不一致的设备混单。
5. 由系统统一计算审批方式、审批链和命中原因。
6. 保留与现有 `authScene` 及后端流程的兼容能力。

## 二、核心设计原则

### 2.1 事实、意图和决策分离

| 层级 | 主要内容 | 产生方式 |
|------|----------|----------|
| 设备事实 | 产品线、设备来源、借测单、当前授权、累计时长、历史次数、已有模块及规格 | 系统查询 |
| 申请意图 | 开通、延长、增开模块、扩大规格或数量 | 用户确认 |
| 审批决策 | 默认放通、人工审批、特殊流程、不允许申请 | 系统计算 |

### 2.2 一张申请单只有一个业务上下文

一张申请单可以包含多个设备，但所有设备必须共享同一申请事项、同一材料要求和同一审批处理方式。无法共享时必须拆分申请。

### 2.3 风险校验以后端为准

前端可以展示预计处理方式，但提交时必须由后端基于最新可信数据重新查询并计算，不能信任前端提交的设备事实或审批结果。

### 2.4 规则结果可追溯

申请单保存审批规则版本和计算快照。规则后续调整后，历史申请仍能还原当时的审批依据。

## 三、字段职责调整

### 3.1 用户可见字段

将当前前置的“授权场景”改为设备识别后的“本次申请事项”。

| 申请事项 | 说明 |
|----------|------|
| 开通授权 | 当前无授权或授权已过期，需要重新开通测试授权 |
| 延长授权 | 延长当前授权有效期 |
| 增开模块 | 在现有授权基础上增加模块 |
| 扩大规格或数量 | 增加容量、点数、CPU 数、接入数量等规格 |

系统根据设备事实过滤明显不适用的事项。例如当前无授权时不展示“增开模块”；当同一设备同时可以增开模块或扩大规格时，由用户明确选择本次目的。

### 3.2 系统事实字段

每台设备形成独立的 `deviceFacts`，至少包含：

| 字段 | 说明 |
|------|------|
| `deviceIdentifier` | 设备 ID、集群 ID、KeyId 或其他产品标识 |
| `productLineId` / `productLineName` | 查询到的实际产品线 |
| `deviceSource` | 借测设备、销售设备、非借测设备或未知来源 |
| `borrowOrderId` | 借测设备关联的借测单号 |
| `authorizationStatus` | 无授权、有效、已过期 |
| `currentModules` | 当前已授权模块 |
| `currentCapacity` | 当前规格或授权数量 |
| `testHistory` | 累计测试时长、历史申请次数和延期记录 |
| `lookupStatus` | 查询成功、无记录、接口异常 |

### 3.3 `authScene` 兼容策略

`authScene` 暂时保留为后端兼容字段，但不再由用户直接选择。系统根据设备事实和 `requestAction` 自动映射：

| 设备事实与申请事项 | 兼容 `authScene` |
|--------------------|------------------|
| 无授权或授权过期后开通 | `1` 开通测试授权 |
| 非销售设备在有效期内延长、增开模块或扩大规格 | `2` 授权资源调整 |
| 销售设备增开模块 | `3` 销售设备增开新模块测试授权 |
| 销售设备扩大规格或数量 | `5` 销售授权扩容测试授权 |
| 销售设备延长授权 | `6` 销售设备申请延长授权 |

该映射仅用于兼容现有数据与流程。审批决策不能只依赖 `authScene`，仍需使用完整规则输入计算。

## 四、产品线下拉框设计

### 4.1 分组规则

产品线下拉框分为两个区域：

1. 在售产品：位于上方，保持正常选项样式。
2. 已退市产品：位于下拉框底部，通过分组标题“已退市产品”与在售产品分隔。

已退市选项显示“已退市”状态标识，但保持可点击、可选择。

### 4.2 当前数据口径

当前以审批规则表“是否已退市”列为准：

1. `WOC` 明确标记为“退市”，归入已退市产品区域。
2. 明确标记为“在售”的产品归入正常区域。
3. 状态为空的产品暂按在售展示，包括当前表格中的 `aBDI`。
4. 后续补全产品状态后，列表按配置自动重新分组，不改变页面结构。

### 4.3 退市提示

选中已退市产品后，在产品线字段下方持续显示：

> 该产品已退市，请确认仍需申请测试授权。

提示不阻止填写和提交，也不单独改变审批流。切换回在售产品后提示自动消失。提交数据需要保留本次选择时的产品状态快照。

## 五、页面主流程

### 5.1 正常流程

1. 用户选择产品线和版本。
2. 页面根据产品线展示对应标识输入方式，例如设备 ID、集群 ID、KeyId 或 info 文件。
3. 用户录入一个或多个设备标识。
4. 系统逐台查询设备事实，并展示识别结果摘要。
5. 所有设备查询完成后，系统计算共同可办理的申请事项。
6. 页面展示“本次申请事项”，由用户确认本次申请目的。
7. 系统根据申请事项展示对应的模块、规格、时长和申请材料。
8. 用户完成填写后，系统展示预计处理方式及主要命中原因。
9. 提交时后端重新查询事实并计算最终审批决策。

### 5.2 设备识别结果

每台设备至少展示：

1. 设备标识和实际产品线。
2. 设备来源及借测关系。
3. 当前授权状态。
4. 已授权模块和当前规格。
5. 累计测试时长及历史申请次数。
6. 查询状态和异常原因。

识别结果用于帮助用户确认，不允许用户直接修改系统查询到的可信事实。

### 5.3 申请事项联动

切换申请事项时，页面必须重置只属于原事项的字段和查询结果，避免隐藏字段残留并随新事项提交。

| 申请事项 | 主要联动内容 |
|----------|--------------|
| 开通授权 | 展示首次授权所需模块、规格、时长及基础材料 |
| 延长授权 | 展示当前授权、累计时长、延期时长及延期说明材料 |
| 增开模块 | 展示当前模块与可增开模块，禁止重复选择已有模块 |
| 扩大规格或数量 | 展示当前规格、目标规格及产品线限额 |

## 六、多设备申请设计

### 6.1 保留的现有能力

1. 设备 ID 和设备 SN 继续使用 Chip 方式批量录入。
2. 输入任一借测设备后，可自动带出同一借测单下的其他设备。
3. 自动带出的设备允许删除，以支持只申请同一借测单中的部分设备。
4. 提交时保存用户最终确认的设备 ID 和设备 SN 列表。

### 6.2 兼容性签名

每台设备查询完成后生成兼容性签名。以下内容必须一致：

1. 产品线和本次选择的版本。
2. 本次申请事项。
3. 设备来源及授权处理类型。
4. 借测设备所属借测单。
5. 所需申请材料集合。
6. 审批决策类型和审批链标识。

同一借测单只代表设备具有关联关系，不代表一定可以合并。系统仍需逐台计算兼容性。

### 6.3 冲突处理

任一设备兼容性签名不一致时：

1. 硬性阻止进入提交状态。
2. 列出冲突设备及具体原因。
3. 用户只能删除冲突设备，或拆分为多张申请单。
4. 不允许通过确认弹窗绕过该校验。

典型冲突包括：

1. 不同借测单。
2. 不同申请事项。
3. 一个设备默认放通、另一个设备需要人工审批。
4. 审批节点不同。
5. 需要提交的证明材料不同。

## 七、查询异常与风险处理

### 7.1 接口异常或超时

1. 展示明确的接口异常状态和重试入口。
2. 允许保存草稿。
3. 不允许绕过设备校验直接提交。
4. 重试成功后重新计算可办理事项和审批决策。

### 7.2 查询成功但无设备记录

1. 允许用户补充必要的设备信息和证明材料。
2. 该申请强制进入人工核验，不能默认放通。
3. 保存查询无记录、人工补录内容和补录人信息。

### 7.3 产品线不一致

设备查询到的实际产品线与用户选择不一致时：

1. 展示用户选择值和系统查询值。
2. 阻止继续填写和提交。
3. 用户需要修正产品线或移除冲突设备。

### 7.4 事实变化

提交时发现设备事实相较页面查询时已变化，后端拒绝按旧结果提交，并返回变化字段。用户刷新设备信息后重新确认申请事项和审批结果。

## 八、审批决策设计

### 8.1 规则输入

审批计算至少使用：

1. 产品线、版本和产品状态。
2. 设备来源、借测关系和当前授权。
3. 累计测试时长、历史申请次数和延期记录。
4. 客户类型、申请人身份、所属区域和办事处。
5. 本次申请事项、申请时长、模块和规格数量。
6. 产品线默认限额、最大限额和特殊产品规则。

### 8.2 规则输出

统一输出：

| 字段 | 说明 |
|------|------|
| `decisionType` | 默认放通、人工审批、特殊流程、不允许申请 |
| `routeKey` | 审批链或特殊处理流程标识 |
| `reasonCodes` | 命中的结构化原因编码 |
| `reasonTexts` | 面向用户和审批人的原因说明 |
| `ruleVersion` | 本次计算使用的规则版本 |
| `calculatedAt` | 计算时间 |

### 8.3 页面展示

提交前展示“预计处理方式”和主要原因，例如：

> 预计需要人工审批：累计测试时长超过 3 个月，命中覆盖市场客户 3 至 6 个月规则。

页面展示仅作预告。最终审批方式、审批链和原因由后端提交校验结果决定。

### 8.4 规则快照

申请单保存：

1. 设备事实快照。
2. 用户提交的申请事项及目标参数。
3. 审批决策输出。
4. 规则版本和命中原因。
5. 产品状态快照。

## 九、系统边界与依赖

### 9.1 外部依赖

1. 设备查询平台：设备属性、产品线、当前授权、模块和规格。
2. 借测系统：借测单、设备清单、借测类型和期限。
3. 客户主数据：客户类型、客户归属和联系人信息。
4. 授权历史：累计测试时长、申请次数和延期记录。
5. 审批规则数据：产品限额、审批链、特殊产品和规则版本。

### 9.2 本方案不包含

1. HTML、JavaScript 或后端代码改造。
2. 外部系统接口开发。
3. 审批规则配置后台。
4. 未在审批规则表中明确的产品线规则补录。
5. 现有 XaaS 申请流程调整。

## 十、验收标准

### 10.1 产品线

1. `WOC` 展示在下拉框底部“已退市产品”区域。
2. 状态为空的产品暂时展示在正常区域。
3. 退市产品可正常选择和提交。
4. 选择退市产品后展示风险提示，切换产品后提示正确消失或更新。
5. 提交数据保留产品状态快照。

### 10.2 设备识别与申请事项

1. 页面不再要求用户在设备识别前选择原“授权场景”。
2. 不同产品线展示正确的设备标识输入方式。
3. 查询完成后展示设备事实摘要和适用申请事项。
4. 同一销售设备可以同时出现“增开模块”和“扩大规格”，由用户选择本次目的。
5. 不适用的申请事项不展示。
6. 切换申请事项后，原事项专属字段和结果不会残留提交。

### 10.3 多设备

1. 同一业务上下文且审批链一致的设备可以批量申请。
2. 同一借测单设备可自动带出并允许删除。
3. 不同借测单、申请事项、材料要求或审批链的设备被硬性阻止混单。
4. 冲突提示能够指出具体设备和冲突原因。

### 10.4 异常与审批

1. 查询接口异常时可以重试和保存草稿，但不能提交。
2. 查询无记录时只能进入人工核验。
3. 查询产品线不一致时不能继续提交。
4. 前端预计审批结果与提交时后端计算结果一致。
5. 历史申请能够还原命中规则、审批原因和规则版本。

## 十一、测试建议

1. 产品线在售、退市和状态为空时的分组与切换。
2. 设备查询成功、无记录、超时及产品线不匹配。
3. 单设备仅一个申请事项和多个可选申请事项。
4. 多设备兼容、不同借测单、不同材料和不同审批链组合。
5. 默认放通、人工审批、特殊流程和不允许申请。
6. 客户类型、累计时长、规格限额及申请次数的边界值。
7. 提交前后设备事实变化导致的重新确认。
8. 审批规则升级后历史规则快照的还原。
9. `requestAction` 到兼容 `authScene` 的映射。
