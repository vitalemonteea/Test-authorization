# 解决方案型测试授权：交叉场景与判定规则（讨论稿）

> 目的：把方案型申请与单品测试授权、销售授权、云服务订阅、借测资产之间的交叉关系转成可判定的规则。本文是建议规则，不代表业务方已确认或当前原型已实现。

## 1. 现状依据与主要缺口

- 《安全方案测试申请规则.xlsx》分别规定了各方案的组合、默认规格、测试次数、延期和审批。例如全球加速/组网为自然年每客户一次，任一产品非首次开通需人工审批；MSS 按区域配额，标准服务测试 15 天且不可延期。
- 单品 V2 需求按产品和授权对象识别首次开通、历史过期后重开、有效期内调整；销售设备是设备来源属性，并非另一套互斥的基础状态。还校验累计时长、申请次数、产品规格及多设备兼容性。
- 现有方案型需求锁定方案产品线、统一授权到期日、整单审批和原子交付，但提交前未定义跨单品/方案/销售授权的存量权益查询与差额计算，也未定义已授权产品如何参与整单交付。
- 单品审批场景表中还有待确认规则，尤其客户类型映射、销售设备例外、设备更换与规模调整。不能把标注“已明确”但处理规则仍写“待确认”的行直接配置成自动放行。

## 2. 核心原则

1. **按权益判断，不按申请入口判断。** 同一设备从单品入口改走方案入口，不能重置历史次数、累计测试天数或审批等级。方案型是业务编排层，底层产品权益仍受产品线规则约束。
2. **先确定授权对象，再查全来源历史。** 设备线使用可信设备 ID/SN 映射；HCI/SCP 使用集群标识；XaaS 使用客户云图租户 ID 与订阅实例；必要时另按客户+方案编码统计方案次数。设备 ID、SN 或手机号不能单独代替稳定身份。
3. **测试权益与正式销售权益分账。** 任何方案动作均不得删除、缩短或覆盖销售授权；新增测试权益必须标明来源、作用模块/容量及起止时间。下游若只能写入一份合并许可证，应先计算合并后的有效权益，并验证撤销测试权益后正式权益保持不变。
4. **只交付经批准的变化量。** 以当前有效权益为基线，对每个产品对象计算新增模块、增量容量、延期区间或新开通；相同权益重复申请不得再次全量开通。没有变化量时明确提示，不生成新授权。
5. **方案整单统一决策，保留逐产品规则。** 每条产品对象先得出“允许/需审批/禁止”与审批原因；任一禁止即整单阻断，其他情况采用覆盖全部命中原因的审批链。不能因为方案首次申请而跳过某个产品的非首次、销售设备、超期或超规格审批。
6. **校验到交付保持一致。** 草稿展示、提交、终审、发号前都需校验历史版本；并发申请须锁定同一授权对象。查询失败、结果不完整或状态不确定时不能当作“无历史”。

## 3. 授权事实与计算口径

每个待授权对象至少建立以下事实：客户主数据 ID、客户类型、方案编码、产品标准 ID、授权对象类型与稳定 ID、设备来源（借测/客户自有/销售）、资产状态与归属、当前正式销售权益、当前测试权益及其来源（单品/方案/其他）、历史测试区间与申请次数、模块/容量、授权状态、借测单与版本、下游中台和事实版本。XaaS 还需云图租户 ID、订阅实例及是否与既有租户合并。

两个不同统计口径应同时存在：

| 口径 | 用途 | 建议统计方法 |
| --- | --- | --- |
| 客户+方案+自然年 | “每客户每年一次”方案准入 | 统计同方案已交付的测试批次；驳回/撤销且未开通不计，补单与失败重试沿用原业务批次 |
| 产品+授权对象+规则范围 | 单品累计时长、次数、当前权益 | 纳入单品和所有方案来源；按产品规则匹配客户/设备/集群/租户，且保留来源以供审计 |
| 客户+服务/方案+冷却期 | MSS 等复测限制 | 从实际测试结束或服务到期日计算，不使用申请日期代替 |
| 正式销售权益 | 基线保护 | 独立于测试次数及累计测试时长；销售设备新增测试模块/扩容/延期仍按销售设备特殊规则审查 |

累计测试时长应按同一对象上**有效测试覆盖日期的并集**计算，避免重叠授权重复累计；申请次数按成功交付的业务批次计，不能用发号调用次数或子产品行数计。若产品规则另有“授权签发天数累计”口径，应逐产品覆盖并明确配置。自然年跨年、跨客户转移、租户迁移与设备换机都必须保留原事实链，不因标识变化自动清零。

## 4. 判定顺序

1. **确认方案准入。** 校验方案版本与启用状态、产品组合和互斥/可选关系、客户与借测单归属及状态、方案次数/配额/冷却期。借测单占用应按“本次业务批次”判重，不应把合法的原单重试误判为新申请。
2. **识别每个授权对象。** 借测单设备只读继承；追加设备也必须查资产来源、销售状态、产品与客户归属，不能因为是手填设备就绕过查验。HCI/SCP 按集群，XaaS 按租户和订阅实例识别。
3. **拉取全来源权益。** 同时查询单品、历史方案、销售及下游实际生效权益；检测重复、归属冲突、待审批/开通中申请、失败但中台状态未知的记录。缺少可信结果时阻断并给出重试/核查入口。
4. **逐对象计算变化。** `当前权益 + 本次申请目标 - 当前权益 = 变化量`，分别求模块、容量与有效期。有效期变更只影响新增测试权益；若请求的方案统一到期日早于现有到期日，不得缩短现有权益。
5. **套用方案规则和单品规则。** 检查首次/重开/调整、销售设备特殊准入、累计时长、次数、规格、产品状态、方案次数与服务配额。多条规则同时命中时保留全部原因，禁止优先于审批，审批优先于自动开通。
6. **决定整单处理。** 所有对象可自动且方案本身可自动，才自动；任一对象需审批则整单走覆盖该原因的审批链；任一禁止或无法识别则整单阻断。逐对象处理差异很大时保留一张方案申请及多条子决策，必要的例外走补充审批；不能默默拆成几个自动单。
7. **提交与发号前重查。** 记录事实快照和规则版本，重新比较当前权益、借测状态和方案配置快照。发生变化则退回申请人确认或重新审批，不按旧快照发号。
8. **幂等交付与补偿。** 只下发变化量，用申请批次+产品对象+动作作为幂等键；若部分产品失败，撤销本次新增的测试权益，不触碰申请前已有的单品、方案或销售权益。超时结果先查中台最终状态，再执行补偿；补偿失败显示“待人工处置”，不能标成已完整回滚。

## 5. 交叉场景矩阵

下表“建议处理”是目标规则。实际能否执行取决于中台是否支持权益增量与精确撤销。

| 场景 | 关键风险 | 建议处理 |
| --- | --- | --- |
| 同客户、同设备、同产品已有**有效单品测试**，再申请方案 | 全量发号叠加模块/容量/时长；掩盖非首次 | 识别为该产品的有效期内调整，展示现有权益和变化量；仅增开/扩容/延期可继续，依单品和方案“任一产品非首次”规则升级审批；无变化量则阻断重复提交 |
| 同产品单品测试**已过期**，再申请方案 | 错当首次，重置累计和次数 | 识别重开，历史计入累计与次数；触发方案非首次审批，超累计再升审或按产品规则禁止 |
| 已有**其他方案**的同产品测试，再申请本方案 | 跨方案重复开通、套用两个方案额度 | 仍按同一产品对象的存量权益计算变化量；两个方案的次数分别统计，产品累计全来源统计；相同权益重叠不可重复交付 |
| 已有本方案测试，再次申请/跨自然年重申 | 规避方案次数或借年底刷新额度 | 同年按延期/变更/复测处理，不算首次；跨年是否重置方案次数只影响方案层，产品累计和冷却期不自动归零 |
| 部分组件已有授权，其他组件首次 | 以“整套方案首次”自动开通全部 | 逐组件识别；任一非首次按方案规则转人工，保留各组件差额和原到期日 |
| 借测单内混有首次设备、有效测试设备、销售设备 | 一个统一动作错误覆盖全部 | 逐设备算动作与审批。借测资产与销售状态矛盾先核查；能形成一套明确的整体审批及变化量才整单继续，不能把销售设备当借测设备处理 |
| 追加设备不在借测单或属于其他客户/产品 | 手填绕过资产审批 | 查询设备身份、归属及产品；归属不符阻断，合法非借测设备按真实来源适用规则；是否允许混入当前借测方案由业务规则明确 |
| 同一设备 ID 与 SN 指向不同资产、集群 ID 变化 | 换标识重置历史 | 核验资产映射与换机/重装证据；无法确认同一对象时阻断，确认后继承历史并记录标识沿革 |
| 销售设备已有**正式授权**，方案申请同模块 | 测试许可证覆盖或缩短正式权益 | 同模块、同/低规格且正式授权覆盖目标期时不发测试授权；方案其余组件可继续，主单记录此组件为“已有正式权益满足”，但是否计入方案完整性交付须确认 |
| 销售设备已有正式授权，方案要求新模块/更高容量 | 测试权益越权扩展销售范围 | 仅申请差额测试权益，走该产品销售设备例外/增开/扩容审批；明确测试到期后退回正式权益，禁止修改正式订单容量 |
| 销售设备已有有效**测试授权**，又申请方案 | 以方案入口规避销售设备续期审批 | 同时命中有效期内调整和销售来源；按销售特殊规则、单品累计、方案非首次一起审查 |
| 已有测试授权的设备后来转销售 | 历史测试码继续延展，或覆盖新正式授权 | 读取销售转化时间及当前正式权益；未过期测试权益保持原边界，新变化按销售设备规则处理；销售授权开通不得被方案回滚撤销 |
| 借测设备已归还/撤销或申请过程中售出 | 已发授权继续使用 | 提交和发号前阻断；已发授权的失效/转销售处置另定联动策略，不能只限制新申请 |
| XaaS 租户已有单品/其他方案订阅 | 租户重复、订阅量叠加或覆盖 | 以云图租户+订阅实例查现有权益，区分新购正式、试用、渠道赠送；只开增量或延长测试部分，不新建重复租户 |
| 客户变更、租户合并/拆分、设备跨客户复用 | 客户维度查询漏历史；权益串户 | 当前申请必须绑定新客户授权对象；对象全局历史用于识别异常和追溯，旧客户权益不得迁入新客户；迁移需单独证据与授权流程 |
| 两张单同时申请同一对象；一张待审批、一张待开通 | 双方都看到“无历史” | 申请时提示占用并阻断相冲突的变化；终审和发号采用对象级锁/版本校验；只允许原单重试沿用幂等键 |
| 原方案部分授权失败后重提 | 重试再次开通已成功组件 | 先对账每个子产品最终状态；若部分权益仍有效，重试只能补齐未交付差额，回滚也只能撤销本批新增权益 |

## 6. 方案特例与现有材料冲突

| 事项 | 现有材料 | 建议落地方式 |
| --- | --- | --- |
| 统一授权到期日 | 方案型 PRD 要求所有产品统一 `authDays`；MSS 规则却是 MSS 15 天、aES/AF/STA 30 天，且 MSS 以上线日计时、不可延期 | “统一申请窗口”与“逐产品权益有效期”分开建模。若业务坚持全部同日到期，先由 MSS 等规则 Owner 明确变更原业务规则，不得让通用 `authDays` 默默覆盖 |
| 首次自动开通 | 全球加速/组网规则规定首次自动，但任一产品非首次转人工；其他方案有独立审批链或配额 | 自动资格需方案层与每个产品层均满足首次及规格；MSS/分布式/数据安全不套用加速方案自动开通规则 |
| 方案次数与产品次数 | 方案按自然年每客户一次；单品按设备/集群/产品历史累计 | 双账本分别判断；同一方案含多产品只计一次方案批次，各产品分别记一次产品测试业务批次 |
| 审批链 | 方案表、单品 V2 表给出不同审批角色，个别单品表仍有空缺 | 审批需覆盖所有命中规则的角色与批准权；同人多角色可去重，禁止以“整单审批”删掉销售/产品/MSS 特批节点。没有唯一审批链时先人工分派，不自动开通 |
| 可选组件与已有权益 | 方案范围锁定，但部分组件可按需关闭；某组件已有正式授权 | 区分“方案要求具备”和“本次需新发测试权益”。已有正式权益可以满足能力要求，但不能在申请单中伪装成本次开通成功 |
| 原子交付 | 方案型 PRD 要求整单回滚；各许可证中台撤销能力尚待确认 | 先验证每条产品线的精确撤销、异步对账和重试能力；不支持者不能承诺技术上的强原子性，应采用编排补偿及人工异常态 |

## 7. 最小验收场景

| 编号 | 给定条件 | 预期结果 |
| --- | --- | --- |
| C01 | AF 单品测试有效至 10 月 31 日；全球组网方案申请 AF+GA 至 10 月 15 日，AF 模块规格不变 | AF 不生成新许可证、不缩短至 10 月 15 日；GA 按首次处理；整单因 AF 非首次进入人工审批 |
| C02 | aTrust 单品测试有效，方案申请新增模块并将容量从 50 提到 80 | 只交付新增模块和容量差额；累计和次数沿用历史；审批显示“有效期内调整+方案组件非首次” |
| C03 | 同一销售 AF 有正式基础模块，方案申请测试新模块 | 正式权益保持原值；新模块按销售设备例外审批，测试到期后自动退回正式权益 |
| C04 | 销售 AF 正式权益已覆盖方案目标模块、规格及期间 | 不再次发号；其他组件照常判定；申请单清楚显示 AF 为“已有正式权益满足” |
| C05 | 同一客户今年已完成全球组网测试，换另一台 AF 再申请同方案 | 方案自然年次数仍命中重复；新 AF 的产品历史另按其对象计算，不因设备更换重置方案次数 |
| C06 | 同一产品当前授权已过期且累计测试超过产品阈值 | 同时显示“重新开通”和“累计超期”，按较严格审批处理，不能因过期当首次 |
| C07 | 两个申请同时针对同一 SN 提交；一个先获批开通 | 后一个在终审/发号前发现事实版本变化，重算差额并重新确认，不能再次全量开通 |
| C08 | 方案子产品 A 发号成功、B 超时，A 在申请前另有销售正式权益 | 先查 B 最终状态；仅撤销本批次 A 的测试增量，A 正式权益保持有效；未知状态不得显示“已回滚成功” |
| C09 | MSS 上次服务到期不足 6 个月，设备授权均为首次 | 整单按 MSS 冷却期规则阻断，不因设备首次而放行 |
| C10 | 云图租户已有 SaaS-XDR 单品试用，方案再申请同租户 SaaS-XDR | 查订阅实例并算差额；无差额则不重复开通，方案审批仍按该组件非首次处理 |

## 8. 优先待确认的三个业务决策

1. **统一到期还是逐产品有效期？** MSS 的 15/30 天与“上线计时”直接冲突于当前方案 PRD 的统一 `authDays`。建议采用统一申请窗口、逐产品权益期限，并由各方案 Owner 确认。
2. **已有正式销售权益可否视为满足方案组件？** 建议允许作为“能力已具备”，但本次不发测试码；若方案考核要求本次新开通每个组件，则此类申请需转人工例外，不得覆盖正式授权。
3. **下游是否能精确查询、增量发号并撤销本批测试权益？** 用一台有正式授权且另有单品测试授权的设备，验证新增模块、撤销本次测试权益、重复调用与超时对账。成功信号是正式授权和原单品测试权益均保持不变；不满足则先限制这类交叉场景上线。

## 9. 实施顺序建议

先做统一授权事实查询、身份映射与“只读冲突提示”，核对单品/方案/销售/云图四类来源的查询覆盖率；再做逐对象变化量和审批规则；最后接入增量发号、精确撤销与对账。首期若数据源或中台能力不足，相关交叉场景直接阻断并转人工处理，不能以“首次申请”默认放行。
