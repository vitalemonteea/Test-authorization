# 激活流程（方案 B）

## 结论

申请阶段不再强制上传 `.info`。申请、审批只依赖业务信息；`.info` 在需要激活授权时再提供。

如果客户已经提前上传过 `.info`，审批通过后直接激活并发出授权文件；如果没有，记录进入「待激活」，由申请人上传，或发链接由外部上传。

激活成功后留存设备信息，后续续期直接复用，不再重复向外部索取文件。

## 状态

| 状态 | 是否需要文件 | 可执行动作 |
|---|---|---|
| 待审批 | 否 | 审批通过 / 驳回 |
| 待激活 | 是（还没有） | 上传设备信息并激活 / 发链接由外部上传 |
| 激活中 | 是（校验中） | 等待结果 |
| 已授权 | 是（已留存） | 下载授权 / 续期 |
| 激活失败 | 是 | 查看原因 / 重新上传 |

原型中审批是即时的，提交后直接进入「待激活」。完整审批链路后续再补。

## 字段权威

- 设备身份（设备 ID、SN、集群标识、型号）：激活时的 `.info` 为准。
- 业务意图（客户、方案、产品线选择、授权时长、模块、场景）：申请表单为准。
- 产品线：表单选择，文件必须匹配；不一致阻断。
- 设备数量：文件解析出的设备数必须与申请设备数一致；不一致阻断。
- 版本/规格：表单为准；文件不一致只提示。

## 设备信息留存

激活通过后写入设备信息记录：

```
DeviceInfo {
  customerId
  productLine
  deviceId
  clusterId
  fileRef
  facts
  source        // applicant | external
  verifiedAt
}
```

按 `客户 + 产品线 + 设备ID` 唯一。续期时先查这条记录：

- 查到且设备未变：直接复用，不再索取文件。
- 设备变化或未查到：进入「上传设备信息」流程。

原型中用 `localStorage` 模拟 `fileRef`，生产环境应存文件服务引用，不直接存文件内容。

## 校验分层

- 申请提交：只校验业务字段，不校验文件。
- 激活：解析文件，校验产品线与设备数量；外部授权平台做最终校验。
- 续期：复用已留存的设备事实；设备变化时才重新上传。
- 外部平台失败：映射为「激活失败」，展示原因，不在本平台复刻其规则。

## 原型改造顺序

1. 申请提交去掉 `.info` 必填与提交前引导。
2. 授权记录新增「待激活」状态和「去激活」动作。
3. 激活弹窗：上传 `.info`，校验通过后生成授权并更新记录。
4. 激活成功后留存设备信息，供续期复用。
5. 中间页从申请链路下线；后续可保留为「激活时发链接」的外部上传能力。

## 当前进度（2026-10-23）

- 申请提交不再要求 `.info` 文件，只要求设备 ID；文件在激活时补充。

- 激活弹窗按单台设备处理：展示本次激活设备 ID，只允许上传 1 个 `.info` 文件，校验产品线与设备信息后立即生成授权，记录变为「已授权」。
- 申请表单的硬件信息、设备 ID、SN 输入提示统一为“每台设备单独提交一次申请 / 每单 1 台设备”。
